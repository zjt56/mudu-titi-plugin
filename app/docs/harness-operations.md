# Harness 批次运维（附加能力）

## 目的与边界

原有录题流水线、Python supervisor、自愈动作、两轮审核和人工上传入口继续工作。新增层在原有自愈无法消除故障时，将当前批次的异常交给 Harness 持久会话调查。正常任务不持续消耗运维模型调用。

运维开关独立保存；关闭只停止新增运维接手，原有录题与自愈继续运行。Harness 服务未挂载或配置损坏时明确显示不可用，不替换原有流程。模型使用显式 operations 角色配置，未单列该角色时使用插件已配置的 default；配置非法不得静默替换服务商或模型。

## 执行证据

事件台账记录批次身份、异常、会话、接手尝试、动作请求标识、结果及验证。安排重试、会话空闲、模型声称修好都不能作为成功。恢复须由后端检查当前产物、记录真实验证证据；仍有标签差异不伪称质量通过。

每个修复请求绑定当前事件、session_id 与 attempt_id。过期接手者不能修改新一轮状态。请求结果未知时查询原请求回执，不换标识盲重发。归档或同名重建后，旧身份不得继续写入；排队续跑也携带原批次身份，在实际执行前再次校验，不能按同名目录误执行新批次。

接手租约为180秒，宿主每15秒续租；单次会话最多10分钟、40次工具动作。无进展释放后按60/180/540/900秒冷却，不持续循环付费。元数据查询和心跳不占全局模型执行锁，实际写产物时才协调原执行/导入锁。续跑使用持久发件记录，重启只恢复队列准入，不重放已执行的修复策略。

历史会话若因已确认的缺失用户消息身份而无法恢复，Host仅在setup尚未执行、错误类型/会话ID/seq10原因为精确匹配且回执已对账时申请一次身份退役。后端再次校验当前租约、同一会话、无任何未知回执以及未曾恢复，保存旧会话标识和原因后清空当前标识，按原冷却重新排队。旧追加式日志保留；下一次认领创建新会话并继续使用原显式模型路线。普通模型、网络、配置和其他恢复错误不触发换会话，也不据此认定故障恢复或质量通过。

## AI 能做什么

通过事件范围内的工具查看诊断，按需读取来源和报告证据，预演并调用已有受控修复，复验，交回原执行队列续跑，记录尚未解决的缺陷。资料内出现的指令作为原文数据，不作为操作授权。

正式批次修改使用已有事务接口及原批次执行锁；不让模型直接编辑台账造完成。续跑到本地边界，不自动上传或发布。

### 故障证据包

`diagnose` 除阶段与错误文本外返回一个自包含证据包：批次名与目录、阶段、失败检查（报告、错误码、检查名、题号、消息）、受影响单元及数量、阶段输入哈希、被读取的来源/输入文件哈希、当前产物哈希、已完成且不受影响的独立阶段、被阻塞的下游阶段、最近尝试记录、升级状态、当前允许的修复与续跑策略、插件代码指纹。这样常见卡点不必从整卷重新调查，也避免修错题。

证据包只读取既有来源、报告和台账，不触发模型调用，不改批次。

### 重复失败升级

每次受控修复或带策略的续跑在写回执时记录一次尝试：动作名、证据指纹、结果（applied/refused/failed）、是否瞬时错误。证据指纹由阶段输入、输入文件内容哈希和插件代码指纹组成。

同一动作在**完全相同的证据与代码**上再次失败时，后端返回 `repeat_without_new_evidence` 并写入 `escalation.kind=code_repair`，不允许原样重试。输入、上游产物或插件代码任一处真实变化后才可以再次尝试；限流、超时、网络、暂时不可用等瞬时错误仍可正常重试。重复计数保存在事件里，跨接手租约有效。

跨轮次有硬预算：同一故障累计 24 次有效尝试、最多 2 次代码安装、最多 6 次局部重生成（被拒绝的请求不计入）。超出后分别返回 `attempt_budget_exhausted`、`install_budget_exhausted`、`regenerate_budget_exhausted`，并把升级方向标为人工；`diagnose` 的 `packet.budgets` 同时给出已用与上限。这样长时间反复接手不会无限消耗模型调用，也不会用不同名字绕过同一条失败路径。预算用尽或需要人做决定时，用 `finish outcome=needs_human` 结束：事件保留证据、置为需人工处理且不再自动接手；它不是修复成功，界面上也不显示为已恢复。

### 隔离代码修复

判断为程序缺陷时，运维会话不获得 shell，也不能直接改运行中的插件；只能请求一个独立代码修复任务：

1. `request_code_repair`：把**当前运行的有效源码**（含未提交修改）复制到临时工作区，保留只读基线副本和可编辑副本，跳过 `.git`、`workflows`、虚拟环境、缓存、密钥样式文件和点文件；同一有效修复尝试复用工作区；安装后必须证明后端进程已更换、重新认领并执行原检查。复验仍失败时，旧记录归档，新请求以当前已安装源码重新捕获基线，允许在总安装预算内进行下一次修复。
2. `code_repair operation=read/write`：只在工作区内读写允许清单中的 `app/workflow/*.py` 与测试文件；拒绝符号链接、`..`、盘符和清单外路径；修改已有文件必须带原文件哈希。
3. `code_repair operation=test`：用固定参数运行指定 unittest，剥除令牌、密钥、密码、API Key、认证变量和 `DSH_*` 环境变量；记录测试指纹，测试后再改文件会使测试证据失效。
4. `code_repair operation=diff/prepare`：输出补丁并生成安装计划；计划要求生产源码自捕获后未变化、无删除、无锁定文件改动、测试通过且测试文件本身被运行过。
5. `install_code_repair`：必须显式确认，且启动插件宿主的进程环境里带 `MD_OPERATIONS_INSTALL=1`（这是运维人员一次性显式开通自动安装的开关；未开通时后端一律拒绝，重启后端也不会改变）。安装前的监听暂停由发布标记 `prepared` 自动完成，不需要人工卡时机。安装前核对计划与当前工作区指纹一致，备份原文件后原子替换，逐个校验哈希；任一步失败自动回滚，新增文件一并删除。结果只标记 `installed_pending_restart`，不直接算修复成功。宿主侧收到 `restart_required` 后立即结束本次尝试并发出 `awaiting_restart`，同时以“等待宿主重启并复验”为由释放接手；重启后再认领并复验，同一次尝试内不得报告 resolved。
6. 发布标记（`<源码根>/.operations-release.json`）：安装前写 `prepared`，全部替换成功写 `installed`（含计划号、文件清单与 journal 路径），回滚写 `rolled_back`。宿主发布协调器轮询该标记：`prepared` 时暂停源码监听、抑制去抖重启；`installed` 时停止后端、只重启一次、等待 `/api/health` 恢复，成功后删除标记并恢复监听；**重启不健康时由宿主按 journal 还原旧文件再启动一次**，成功则恢复旧代码并清除标记，还原失败或还原后仍不健康才写回 `failed` 并停止自动重试，交由人工处理，绝不以重启循环冒充修复。宿主与后端都使用源码根目录的同一标记；时间支持后端实际写入的 ISO 日期及旧秒/毫秒时间戳。还原前先检查全部目标和全部备份的哈希、允许路径及符号链接，再暂存整批旧文件并原子替换；普通 I/O 或替换失败时恢复安装后版本，不能留下旧新文件混合。文件已被他人修改、备份缺失/损坏或存在越界/链接时，在改动任何正式文件前拒绝。超过 5 分钟仍未完成的 `prepared` 视为崩溃遗留，不再永久暂停监听。卸载插件时停止协调器，不能在卸载后继续触发重启。这里保证普通执行失败的补偿事务，不声称多文件替换对断电或进程强杀具备原子性。

锁定文件（运维模块自身、契约、清单、调度、自愈等）不可由该流程修改。`lib/*.js`、配置和数据结构不在自动发布范围；宿主 JavaScript 目前没有经过验证的热更新契约，只能产出补丁，不能承诺自动生效。该工作区不是操作系统沙箱：测试与被测代码仍是可执行代码，所以安装必须由受控宿主在暂停监听、排空执行后单次重启完成。

重启并重新认领事件后仍要执行原有复验：原失败检查通过、产物未过期、输入哈希未变、消费者校验通过，才能标记恢复；部署成功不算修复成功。若批次已归档、停止或身份变化，则不再续跑，保留已部署代码并说明该批次未处理原因。安装与认领记录绑定后端进程身份（PID 加进程世代，模块重载不改变）；同一进程重新认领不算重启，旧进程尝试也不能在重启后继续使用。真正更换进程并重新认领才进入 `restarted_pending_verify`；原检查通过记 `verified`，失败记 `failed` 并允许下一次隔离修复。事件结束时，修复记录随处置一起落账：交人工记 `needs_human`，确认仍需深入修复记 `failed`，不会长期停在 `installed_pending_restart` 被误读为已完成。

未知程序缺陷且未取得修复证据时，必须保留可复现证据和待深入修复状态，不能以重试同一故障替代实际修复。

### 局部重生成

内容阶段的题目级错误不必整卷重跑。运维会话的 `operations_regenerate_units`（后端动作 `regenerate_units`）接受 `target_stage`（缺省时由结构化错误定位生产者）和可选的 `unit_ids`：

- 只允许答案、解析、题型、知识点、听力五个内容阶段；上传/发布边界与确定性阶段一律拒绝；
- 审核差异（一审/二审与原标签不一致）是审核产出，不是内容故障：事件本身来自 `review`/`review_gate` 时拒绝局部重生成（`review_differences_are_output_not_blocker`），不得用自动改标签/改判通过来消除差异；差异保留给人工判断，且不阻断用户手动上传；
- 显式题号必须属于当前批次，未知题号整单拒绝，不静默忽略；
- 未指定题号时只使用证据里真实出现的单元，定位不到就报 `regenerate_units_requires_scope`，不扩大到整卷；
- 写入的反馈文件标明 `scoped_units=true` 和具体题号；CLI 与通用文件任务都只向模型提供这些单元作为输出范围，原文及必要边界证据保留。导入器拒绝范围外的题号/单元，从精确哈希绑定的原产物保留其余单元，复验完整覆盖后才写正式产物；缺少或无法验证范围外基线时拒绝扩大为整卷重跑。答案、解析、题型、知识点、听力映射共用此范围契约；听力仍只能引用已切段且有有效证据的文件，不凭模型输出伪造切段。
- 同一阶段、同一题号集合在相同证据与代码上尚在排队/执行时返回 `already_scheduled`，不重复入队。实际执行结束后记录 `failed` 或 `succeeded`，成功还需真实复验；失败后在相同证据上再次申请会升级，不能永远被误当作排队中。反馈或重新排队部分写入后出现异常保留未知回执，不把部分修改谎报成可随意重发的确定失败。

该动作只缩小重跑范围，不降低校验：阶段仍须自己产出并通过原有检查，产物之外的字段不会被本动作改写。

运维和 self_heal 提示词均要求写前给出当前失败检查/错误码、批次与题号；不能从历史事件、模型建议或差异数量推断内容修复授权。三个审核差异码即使携带 `field=knowledge` 或 `producer_stage`，生产者定位仍返回空，不得通过 `upstream_rederive` 等其他动作绕过保护。审核协议失败只修响应/补齐未完成目标；旧 `execution_completed`、0 卡点或空队列不证明当前审核和最终格式阶段完成。

## 界面

批次旁的 AI 运维区域分别显示服务状态与批次接手状态。服务状态包含启用待命、正在接手数量、最近成功扫描时间、扫描失败；批次状态区分排队、冷却等待、调查、修复、复验、等待续跑、租约过期和待核对动作回执。每5秒后台扫描、面板每3秒读取，正常流程无需持续调用运维模型。最近业务动作和最近心跳分别显示，心跳不得覆盖修复阶段；未知回执明确显示隔离原因，不能宣称已恢复。还显示最近事件、验证证据和关联会话标识。没有明确支持的 Harness 导航契约时提供会话标识复制，不构造虚假的会话链接。开关失败必须显示原因并保留实际状态。

## 验证要求

使用临时目录和模拟 Harness/模型验证：单次接手、重复事件去重、会话恢复、租约过期、旧尝试拒绝、未知请求回执、停止与再次开启、真实复验才可完成、原有自愈与远端上传边界不变。真实卷只在明确目标和授权范围内执行；单测不得调用真实模型或改写用户批次。

快速纠错另需覆盖：证据包含阶段、失败检查、输入与代码指纹及独立/下游阶段；同一证据上的重复修复被拒并升级；输入或代码变化后允许再次尝试；局部重生成只接受内容阶段与已知题号，未定位到题目时拒绝而不是整卷重跑，重复入队被识别；代码工作区拒绝清单外、符号链接和越界路径；测试通过是安装前提且改文件后测试失效；未确认或未开启安装开关时不写生产文件；安装失败自动回滚；安装后只进入待重启状态，重启后仍须原检查复验才算恢复。安装流程的测试必须指向假源码根目录，绝不能改写真实插件。`app/workflow/test_operations_development.py` 与 `app/workflow/test_operations.py::FastRepairOperationsTests` 覆盖上述路径。
