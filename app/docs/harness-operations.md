# Harness 批次运维（附加能力）

## 目的与边界

原有录题流水线、Python supervisor、自愈动作、两轮审核和人工上传入口继续工作。宿主运维服务在线且模型配置有效时，首个确定性阻断异常在执行器安全检查点立即建单，不再等待普通自愈先失败数次；执行器让出故障阶段，待执行锁释放后由 Harness 持久会话分析。模型先在后台保存原因、证据与修改方向，再自动执行已授权的修复、复验、续跑。前台只呈现真实运行状态与结果，不要求展示修改建议，也不以用户阅读建议或逐次确认为推进前提。正常任务不持续消耗运维模型调用。宿主每2秒扫描并报告可用性，超过20秒未更新、关闭或配置无效时不再让出故障给不可用服务，原自愈继续工作；已生效修复租约仍按原有效期与锁保护。首次异常接手并不取消执行锁，长时间独立任务仍需到安全检查点后才能认领。

运维开关独立保存；关闭只停止新增运维接手，原有录题与自愈继续运行。Harness 服务未挂载或配置损坏时明确显示不可用，不替换原有流程。模型使用显式 operations 角色配置，未单列该角色时使用插件已配置的 default；配置非法不得静默替换服务商或模型。

## 调查与修复分离

节点失败后的下一安全边界即发布故障，不等待整轮慢分支收尾。宿主先以 `mode=investigation` 认领：只允许诊断、读证据与记录发现，短时运维台账锁不占批次执行锁，正常独立阶段继续。调查租约不阻止自动推进。

记录具体发现后，宿主通过 `promote` 请求独占修复。后端取得原执行锁，重新校验批次身份、输入快照、代码指纹、预算和未知回执，轮换 attempt/fence；确认成功后宿主才开放原修复工具。等待锁时只等待，不盲重发未知操作；相同证据已有有效调查记录时可直接再次申请升级，不重复烧调查模型。默认不带mode的旧claim仍按repair处理。

完成本地任务后，程序按保守固定阈值（总跨度至少600秒且某模型相关阶段至少180秒）保存独立 `workflow/operations-performance.json`。它只读manifest时间与摘要，不是历史统计异常，也不证明模型故障。报告明确 `investigation_status=not_started`、只读且不可升级修复；本版尚未添加性能专用AI调查队列，不自动重跑慢任务或覆盖故障单。

## 执行证据

事件台账记录批次身份、异常、会话、接手尝试、动作请求标识、结果及验证。安排重试、会话空闲、模型声称修好都不能作为成功。恢复须由后端检查当前产物、记录真实验证证据；仍有标签差异不伪称质量通过。

每个修复请求绑定当前事件、session_id 与 attempt_id。过期接手者不能修改新一轮状态。请求结果未知时查询原请求回执，不换标识盲重发。归档或同名重建后，旧身份不得继续写入；排队续跑也携带原批次身份，在实际执行前再次校验，不能按同名目录误执行新批次。

批次执行锁竞争发生在动作准入前时，后端返回 HTTP 409，并明确 `code=worker_busy`、`admitted=false`、`retryable=true` 和批次名称/目录。宿主仅凭这组结构化证明，以同一请求标识最多等待10秒（默认每500毫秒一次），不记为动作结果未知；仍忙则显示“等待执行锁”，结束本轮并在后续安全认领时接续。认领忙直接等下一次扫描，不创建模型会话。心跳只在后端返回的真实租约期限内等待，不能自行延长租约；释放尚未准入显示“等待释放锁”。网络断连、普通 HTTP 错误、动作体内部异常或仅包含 worker_busy 的文字都不构成安全重发证据；已有未知回执也不能被后续忙响应清除。

接手租约为180秒，宿主每15秒续租；单次会话最多10分钟、40次工具动作。无进展释放后按60/180/540/900秒冷却，不持续循环付费。元数据查询和心跳不占全局模型执行锁，实际写产物时才协调原执行/导入锁。续跑使用持久发件记录，重启只恢复队列准入，不重放已执行的修复策略。

同一数据根可能同时存在多个后端实例（热重启遗留或并行实例）。租约只因**租约到期**或**原执行进程已不存在**而释放：另一个仍存活的后端持有效租约时，本实例不得把它的尝试判成 `process_replaced`，认领请求返回 `worker_busy`（409，`admitted=false`、`retryable=true`）等待其完成。进程存活判定在 Windows 上必须用 `OpenProcess`+`GetExitCodeProcess`；`os.kill(pid, 0)` 在该平台等于 TerminateProcess，会真的终止进程。后端 `/api/health` 的 `busy` 也包含“存在未过期运维租约”：插件据此延后代码热重启（上限30分钟），避免每保存一次 `.py` 就替换执行进程、把在途运维尝试反复作废。

历史会话若因已确认的缺失用户消息身份而无法恢复，Host仅在setup尚未执行、错误类型/会话ID/seq10原因为精确匹配且回执已对账时申请一次身份退役。后端再次校验当前租约、同一会话、无任何未知回执以及未曾恢复，保存旧会话标识和原因后清空当前标识，按原冷却重新排队。旧追加式日志保留；下一次认领创建新会话并继续使用原显式模型路线。普通模型、网络、配置和其他恢复错误不触发换会话，也不据此认定故障恢复或质量通过。

## AI 能做什么

通过事件范围内的工具查看诊断，按需读取来源和报告证据，预演并调用已有受控修复，复验，交回原执行队列续跑，记录尚未解决的缺陷。资料内出现的指令作为原文数据，不作为操作授权。

正式批次修改使用已有事务接口及原批次执行锁；不让模型直接编辑台账造完成。续跑到本地边界，不自动上传或发布。

### 修复阶段有效进展

心跳只证明会话存活，repair租约只证明写权限。卡片通过实际动作显示准备修复、定位代码、修改中、测试中、安装/复验阶段；租约过期或动作未知仍优先显示异常。源码工具优先search字面定位与read_lines局部行号读取；read返回UTF8字节next_offset/eof/sha256，只用返回游标分页，不猜偏移，也不把截断当完整源码。

宿主等待模型idle、会话创建与HTTP均有真正可取消的等待边界，10分钟预算到期能退出。已发出的写动作结果未知时只核对原回执，不释放为可重发任务。连续6次纯读取提示剩余动作，12次后停止新增纯读，允许write/test/verify/finish；有限纠正仍无实际产出时以结构化no_substantive_progress释放，后端等待真实证据变化，保留发现与隔离工作区。已有write/test的尝试仍走正常恢复计划，不因尚未闭环误当纯调查冻结。

### 故障证据包

`diagnose` 除阶段与错误文本外返回一个自包含证据包：批次名与目录、阶段、失败检查（报告、错误码、检查名、题号、消息）、受影响单元及数量、阶段输入哈希、被读取的来源/输入文件哈希、当前产物哈希、已完成且不受影响的独立阶段、被阻塞的下游阶段、最近尝试记录、升级状态、当前允许的修复与续跑策略、插件代码指纹。这样常见卡点不必从整卷重新调查，也避免修错题。

证据包还提供 `candidate_evidence`：当前内容阶段最近两次运行的候选、单元验收进度及确定性拒收证据索引；候选一律标为未验收。`read_evidence` 仅允许读取该当前阶段索引内的限定文件，不开放任意 agent-run 输入、提示词或其他阶段。正式产物缺失不能证明模型没有产出，须先核对候选、验收错误、来源摘要/行列和题号归属。证据包只读取既有来源、候选、报告和台账，不触发模型调用，不改批次。

内容五阶段的 `retry_stage`、换上下文、刷新输入、上游重派生及知识点修正等别名均使用受控局部范围校验；无受影响单元则拒绝，保留已验证基线，不因换动作名重跑整卷。结构化 `retryable=false`、`failure_class=source_binding/validator_fault` 表示来源或校验器问题，保留候选并升级来源/隔离代码修复，不能靠重复生成消化。普通错号、错坐标、改写仍允许局部模型纠正；仅有 `EXPLANATION_SOURCE_UNVERIFIED` 错误码不能断言来源冲突。

### 重复失败升级

每次受控修复或带策略的续跑在写回执时记录一次尝试：动作名、证据指纹、结果（applied/refused/failed）、是否瞬时错误。证据指纹由阶段输入、输入文件内容哈希和插件代码指纹组成。

同一动作在**完全相同的证据与代码**上再次失败时，后端返回 `repeat_without_new_evidence` 并写入 `escalation.kind=code_repair`，不允许原样重试。输入、上游产物或插件代码任一处真实变化后才可以再次尝试；限流、超时、网络、暂时不可用等瞬时错误仍可正常重试。重复计数保存在事件里，跨接手租约有效。

跨轮次有硬预算：同一故障当前证据累计 24 次有效尝试，整个故障记录最多 2 次代码安装、最多 6 次局部重生成（被拒绝的请求不计入）。超出后分别返回 `attempt_budget_exhausted`、`install_budget_exhausted`、`regenerate_budget_exhausted`；`diagnose` 的 `packet.budgets` 同时给出已用与上限及累计尝试。预算用于阻止同证据空转，不作为转人工接管的出口：未修复事件自动进入自治恢复计划，优先隔离代码修复；无可执行的新策略或同一调查无真实进展时进入 `waiting_evidence`，保留证据，真实输入或代码变化后才重新准入。不得仅换会话、改摘要或清空计数绕过预算。兼容接收旧 `finish outcome=needs_human/needs_deep_repair`，但归入自治恢复队列；没有修复及原检查复验证据不得显示已恢复。审核差异仍是输出，不进入此故障恢复链路。

### 本地自治授权

自治开关与运维服务启停分别保存。`<源码根>/.operations-autonomy.json` 使用 `md-operations-autonomy/v1`，记录严格布尔 `enabled`、规范化 `source_root`、授权说明 `authorization` 和更新时间。文件缺失默认关闭；损坏、错根或符号链接配置拒绝授权，不静默当作已启用。该点文件不会复制到隔离工作区，也不在修复读写允许清单中，模型不能自行授权。测试进程会剥除旧安装环境变量和凭据。

可信本地宿主/配置入口调用 `workflow.operations_development.set_autonomy(source_root, enabled=True, authorization="用户明确授权的本地自治修复")` 原子持久化；同一 API 传 `enabled=False` 撤销。`autonomy_config(source_root)` 查询实际配置，`install_authorization(source_root, confirm=False)` 返回 `allowed/autonomous/mode/config_path/authorization`；`mode` 区分 `local_autonomy`、`legacy_confirmed` 和 `disabled`。这些 Python API 是可信本地配置边界，不向事件模型暴露设置授权的工具。当前用户本轮已明确授权本机自治修复，由本地配置入口启用此开关；代码默认值仍保持关闭。

已启用自治时，受控工作流自动完成隔离复现、修改、测试、安装计划、安全安装、宿主重启、重新认领和原失败检查复验。关闭授权不更改既有批次产物，不取消已写入的回滚证据；后续安装重新检查授权。没有任何路径因此获得自动上传、发布、直接编辑用户数据或裁决审核差异的权限。

### 隔离代码修复

判断为程序缺陷时，运维会话不获得 shell，也不能直接改运行中的插件；只能请求一个独立代码修复任务：

1. `request_code_repair`：把**当前运行的有效源码**（含未提交修改）复制到临时工作区，保留只读基线副本和可编辑副本，跳过 `.git`、`workflows`、虚拟环境、缓存、密钥样式文件和点文件；同一有效修复尝试复用工作区；安装后必须证明后端进程已更换、重新认领并执行原检查。复验仍失败时，旧记录归档，新请求以当前已安装源码重新捕获基线，允许在总安装预算内进行下一次修复。
2. `code_repair operation=read/write`：只在工作区内读写允许清单中的 `app/workflow/*.py` 与测试文件；拒绝符号链接、`..`、盘符和清单外路径；修改已有文件必须带原文件哈希。
3. `code_repair operation=test`：用固定参数运行指定 unittest，剥除令牌、密钥、密码、API Key、认证变量和 `DSH_*` 环境变量；记录测试指纹，测试后再改文件会使测试证据失效。
4. `code_repair operation=diff/prepare`：输出补丁并生成安装计划；计划要求生产源码自捕获后未变化、无删除、无锁定文件改动、测试通过且测试文件本身被运行过。
5. `install_code_repair`：用户已明确授权并启用本地持久自治开关时，自动安装，不再要求逐次 `confirm` 或 `MD_OPERATIONS_INSTALL=1`。未启用自治时保留“显式 `confirm=true` 且宿主环境 `MD_OPERATIONS_INSTALL=1`”的旧通道，缺少授权一律拒绝；默认不会给其他源码根全局安装权限。自治安装再次检查本地授权、测试指纹与变更测试执行证据，不复用已失效的测试。安装前的监听暂停由发布标记 `prepared` 自动完成，不需要人工卡时机。安装前核对计划与当前工作区指纹一致、生产源码仍等于基线，备份原文件后以 CAS 检查和原子替换安装，逐个校验哈希；任一步失败自动回滚，新增文件一并删除。安装 journal 记录授权方式。结果只标记 `installed_pending_restart`，不直接算修复成功。宿主侧收到 `restart_required` 后立即结束本次尝试并发出 `awaiting_restart`，同时以“等待宿主重启并复验”为由释放接手；宿主自动重启后再认领并复验，同一次尝试内不得报告 resolved。
6. 发布标记（`<源码根>/.operations-release.json`）：安装前写 `prepared`，全部替换成功写 `installed`（含计划号、文件清单与 journal 路径），回滚写 `rolled_back`。宿主发布协调器轮询该标记：`prepared` 时暂停源码监听、抑制去抖重启；`installed` 时停止后端、只重启一次、等待 `/api/health` 恢复，成功后删除标记并恢复监听；**重启不健康时由宿主按 journal 还原旧文件再启动一次**，成功则恢复旧代码并清除标记，还原失败或还原后仍不健康才写回 `failed` 并停止重复重启，保留 journal、健康检查和恢复证据供后续自治隔离修复；没有新的有效证据不得重复同一安装或伪称恢复，绝不以重启循环冒充修复。宿主与后端都使用源码根目录的同一标记；时间支持后端实际写入的 ISO 日期及旧秒/毫秒时间戳。还原前先检查全部目标和全部备份的哈希、允许路径及符号链接，再暂存整批旧文件并原子替换；普通 I/O 或替换失败时恢复安装后版本，不能留下旧新文件混合。文件已被他人修改、备份缺失/损坏或存在越界/链接时，在改动任何正式文件前拒绝。超过 5 分钟仍未完成的 `prepared` 视为崩溃遗留，不再永久暂停监听。卸载插件时停止协调器，不能在卸载后继续触发重启。这里保证普通执行失败的补偿事务，不声称多文件替换对断电或进程强杀具备原子性。

锁定文件（运维模块自身、契约、清单、调度、自愈等）不可由该流程修改。`lib/*.js`、配置和数据结构不在自动发布范围；宿主 JavaScript 目前没有经过验证的热更新契约，只能产出补丁，不能承诺自动生效。该工作区不是操作系统沙箱：测试与被测代码仍是可执行代码，所以安装必须由受控宿主在暂停监听、排空执行后单次重启完成。

重启并重新认领事件后仍要执行原有复验：原失败检查通过、产物未过期、输入哈希未变、消费者校验通过，才能标记恢复；部署成功不算修复成功。若批次已归档、停止或身份变化，则不再续跑，保留已部署代码并说明该批次未处理原因。安装与认领记录绑定后端进程身份（PID 加进程世代，模块重载不改变）；同一进程重新认领不算重启，旧进程尝试也不能在重启后继续使用。真正更换进程并重新认领才进入 `restarted_pending_verify`；原检查通过记 `verified`，失败记 `failed` 并允许下一次隔离修复。事件未修复时，修复记录随处置落账为 `failed`，并进入下一步自治恢复计划；旧人工处置仅保留原始来源记录，不生成必须人工接管的终态，也不会长期停在 `installed_pending_restart` 被误读为已完成。

未知程序缺陷且未取得修复证据时，必须保留可复现证据和待深入修复状态，不能以重试同一故障替代实际修复。

### 局部重生成

内容阶段的题目级错误不必整卷重跑。运维会话的 `operations_regenerate_units`（后端动作 `regenerate_units`）接受 `target_stage`（缺省时由结构化错误定位生产者）和可选的 `unit_ids`：

- 只允许答案、解析、题型、知识点、听力五个内容阶段；上传/发布边界与确定性阶段一律拒绝；
- 审核差异（一审/二审与原标签不一致）是审核产出，不是内容故障：事件本身来自 `review`/`review_gate` 时拒绝局部重生成（`review_differences_are_output_not_blocker`），不得用自动改标签/改判通过来消除差异；差异保留给人工判断，且不阻断用户手动上传；
- 显式题号必须属于当前批次，未知题号整单拒绝，不静默忽略；
- 未指定题号时只使用证据里真实出现的单元，定位不到就报 `regenerate_units_requires_scope`，不扩大到整卷；
- 写入的反馈文件标明 `scoped_units=true` 和具体题号；CLI 与通用文件任务都只向模型提供这些单元作为输出范围，原文及必要边界证据保留。导入器拒绝范围外的题号/单元，从精确哈希绑定的原产物保留其余单元，复验完整覆盖后才写正式产物；缺少或无法验证范围外基线时拒绝扩大为整卷重跑。答案、解析、题型、知识点、听力映射共用此范围契约；听力仍只能引用已切段且有有效证据的文件，不凭模型输出伪造切段。
- 同一阶段、同一题号集合在相同证据与代码上尚在排队/执行时返回 `already_scheduled`，不重复入队。实际执行结束后记录 `failed` 或 `succeeded`，成功还需真实复验；失败后在相同证据上再次申请会升级，不能永远被误当作排队中。反馈或重新排队部分写入后出现异常保留未知回执，不把部分修改谎报成可随意重发的确定失败。

该动作只缩小重跑范围，不降低校验：阶段仍须自己产出并通过原有检查，产物之外的字段不会被本动作改写。

运维和 self_heal 提示词均要求写前给出当前失败检查/错误码、批次与题号；不能从历史事件、模型建议或差异数量推断内容修复授权。三个审核差异码即使携带 `field=knowledge` 或 `producer_stage`，生产者定位仍返回空，不得通过 `upstream_rederive` 等其他动作绕过保护。审核协议失败只修响应/补齐未完成目标；旧 `execution_completed`、0 卡点或空队列不证明当前审核和最终格式阶段完成。

## 界面

AI 运维卡片仅显示一个真实状态和一句简短提示，保留启停与刷新；不显示展开事件、日志区、会话标识及冗余说明。正常且已确认扫描时显示“持续监测中”；异常时区分已触发、调查中、等待修复锁、修复中、复验中、已恢复等。关闭、失联、配置失败或回执未知不能伪装为持续监测或已恢复。故障提示仍含具体批次与目录。流程图上方移除进度更新等小字，12类主图与悬浮真实子流程保留。

后台原因、证据与修改方向继续留档；任何建议不构成人工审批步骤。宿主每2秒后台扫描、面板每3秒读取，正常流程不持续调用运维模型。心跳不得覆盖真实修复阶段；只有后端原检查复验才能显示恢复。未知回执、断连、失租约或预算耗尽时不盲续发。

## 验证要求

使用临时目录和模拟 Harness/模型验证：单次接手、重复事件去重、会话恢复、租约过期、旧尝试拒绝、未知请求回执、停止与再次开启、真实复验才可完成、原有自愈与远端上传边界不变。真实卷只在明确目标和授权范围内执行；单测不得调用真实模型或改写用户批次。

快速纠错另需覆盖：证据包含阶段、失败检查、输入与代码指纹及独立/下游阶段；同一证据上的重复修复被拒并升级；输入或代码变化后允许再次尝试；局部重生成只接受内容阶段与已知题号，未定位到题目时拒绝而不是整卷重跑，重复入队被识别；代码工作区拒绝清单外、符号链接和越界路径；测试通过是安装前提且改文件后测试失效；默认未授权时不写生产文件，本地自治授权后不带 `confirm`/环境变量也可安全安装；授权撤销、损坏或错根时拒绝，旧确认加环境变量模式兼容；自治配置不能通过修复 read/write 工具读取/改写，也不复制到工作区，测试进程不继承旧安装开关；安装失败自动回滚；安装后只进入待重启状态，重启后仍须原检查复验才算恢复；旧人工终态进入自治恢复，预算与同证据无进展保护不会伪报成功。安装流程的测试必须指向假源码根目录，绝不能改写真实插件。`app/workflow/test_operations_autonomy_development.py`、`app/workflow/test_operations_development.py` 与运维/宿主专用回归覆盖上述路径。
